# 2210020 SURICATA STREAM ESTABLISHED packet out of window
Volume: 471.4/day (3300/week, identical in weeks 1 and 2), sources 60, destinations 4, working hours 41% (week 2: 40%); current level 3 (stock rule 86601, no ladder match: no signature_severity/confidence metadata, so it is already below the visible level 6)   [evidence: demo data, week 1 and 2 snapshots; raw eve aggregates, weeks 1 and 2]
What it matches: [static] tcp, any -> any, `stream-event:est_packet_out_of_window` (engine stream event, no content or buffer match), `threshold: type backoff, track by_flow, count 1, multiplier 10` (alerts on the 1st, 10th, 100th ... event per flow), classtype protocol-command-decode, no metadata. It says the TCP stream engine saw a packet of an established flow outside the receive window. It does not say why: packet loss or reordering on the capture path, asymmetric/partial mirroring, a broken or odd TCP stack, or deliberate TCP evasion/injection all look identical. It does not prove an attack, and it does not prove a problem on the monitored hosts.
Observations (demo data, week 1 and 2 snapshots plus raw eve counts, mapped to `inventory/hosts.md`):
- Port 443 only (3300/3300 each week), app_proto "tcp" (no TLS parsing in these events), one alert per flow (3300 flow_ids, 3300 events: the backoff threshold means we only see the first event of each flow).
- Sources: 60 workstations in 10.10.100.0/24 (DHCP, not stable identities), 41-74 events each per week, no outlier. Destinations, an even split of about 800-860 per week each: 10.10.20.30 print01, 10.10.20.15 files01, 10.10.0.10 dc1 (all inventory, with owner) and 198.51.100.20 (not in the inventory, external address).
- Same shape in both weeks (same totals, 60 sources, 4 destinations, 240 pairs). No new source, no spike, no single host with a burst.
- Fact: the spread is uniform over sources and destinations, internal and external alike. Hypothesis (unverified): a property of the capture path (loss or asymmetry on the mirror port) or of the traffic generator in this demo, not of one host. Nothing in the data separates that from a mild evasion attempt; it only shows there is no outlier.
- Data limit: the snapshot and the eve events have no TCP flags, window, sequence numbers or flow state; direction of the offending packet is unknown. Eve event shows rev 1, the rule text given for this task says rev 3 - the sensor ruleset version should be confirmed (static text vs live events). [Fixed after triage: the demo generator wrote rev 1 for every SID; it now writes the real revisions.]
What the analyst does: for a single alert, nothing: there is no host to isolate or account to check, and it cannot be resolved from the alert. It has value only as a trend. A rate that rises on one sensor (capture health: mirror loss, sensor overload, `stats` drop counters) means Suricata is blind for part of the traffic - this is for the sensor owner. A burst from one source towards one server, or the same flow repeating at each backoff step (1, 10, 100), would point to TCP evasion/injection (T1562 / T1027-type) and needs a packet capture of that flow.
Decision: ASK - the per-alert answer is "nothing", so it must not be visible at level 6, and it already is not (level 3). But it is not DISABLE: the signature is a capture-health and evasion indicator, and nothing in the repository shows a control that would replace it (see below). It is also not LOWER: there is no change to implement (already below visible), no single verified route (the pattern is every pair on :443, a Cartesian "everything"), the sources are DHCP addresses, and 198.51.100.20 is not in the inventory.
Question for the sensor owner / Network (mirror and sensor): "Is capture health monitored today - Suricata `stats.log`/eve `stats` (kernel_drops, `stream.est_packet_out_of_window`, tcp reassembly gaps) or SPAN/TAP port counters - with an alert when drops rise? If not, can we add one?" Question for IT (inventory): "Who owns 198.51.100.20 and why do all 60 workstations talk to it on 443 (proxy, cloud service)?"
Proposed after the answers: if capture health is monitored with an alert -> leave at level 3 (no rule, no change), keep the signature enabled and in the archives so it can be hunted. If it is not monitored -> do not hide it silently: keep level 3 and add a rate-based (aggregate) check via `siem-query`: out-of-window events per hour per sensor, and per source -> destination pair; review when a single pair exceeds a baseline taken from these weeks (about 20 per pair per week now; the threshold is for the owner to set). Never DISABLE on the sensor and never suppress by IP or subnet.
